# Overall User Experience Changes

> Latest Interview with Falih | November 21st, 2026

## What Is This?

This is a note from my latest interview with Falih after showing the latest state of the prototype. The note is split into the renewal steps in the prototype. The note basically contains what Falih said would improve the app to simplify the workflow so we can have a more stable MVP (minimum viable product).

## Important

We should have the "tour" feature again for first time users. This feature should be reaccessible again and again under the user menu (right below case list).

## 1. Renewal Materials

### QS Overview

- **Falih's Quote:** I want AI to play a more significant role here. I want the *"First Things First"* to be: AI Check the previous period's Final Slip (or Cover Note) against the latest Standard T&C that the Insurance Broker already have.
   - **Desired Outcome:** AI can flag the difference between the Final Slip/Cover Note (from the previous period) vs the Standard T&C, then the human user can simply decide whether to take the clause from the T&C and put it into the Quotation Slip (QS).
- **Irfan's Interpretation**: I think we could add more features:
   - A way to store the latest T&C that the broker has (with version control), like a single living document that the app can refer to every time we want to check against the T&C.
   - A **Superadmin** role per company that manages user roles and privileges (brokers and clients). This superadmin should (by default) have the ability to update Standard T&C. The Standard T&C privilege could also be given to other users assigned by the Superadmin.

### Wording

- **Falih's Quote:** I think the "Wording" part in step 1 is not strictly necessary at this point. Becuase we already have a standard set of words to use inside our Standard T&C. This could go in the "Standard T&C" settings so we don't have to check wording again.

### Terms & premium

- **Falih's Quotes:**
   - The Final Slip should state any discounts, but we can still remove this from the QS (still go with the gross premium). Insurers don't really have to know how much discount the broker is giving to the client. For property all risk (PAR), 15% discount to the client is imperative.
   - Because we normally use Excel, I think it's good if we can upload the Excel file, then it could be embedded inside the Quotation Slip Word file beautifully.
   - It would be super helpful if the AI can match the Excel file (addresses, occupancy, rate) with OJK rules (See: https://ojk.go.id/id/kanal/iknb/regulasi/asuransi/surat-edaran-ojk/Documents/SAL%20-%20Lampiran%20I%20-%20Property%20Amandemen.pdf)
- **Irfan's Interpretation:**
   - Maybe the app can have a standard Excel template the broker can download, then upload it again with their data. OR, AI can handle that Excel scanning and have a pop-up window so the human user can confirm before going forward.
   - The **Desired Outcome:** Human users (broker) can download the final Quotation Slip (Word file) and immediately send it to the insurer.

## 2. Insurer Review

- **Falih's Quotes:**
   - Usually, when we send QS to the insurers, they would return to us with an annotated PDF of the QS (maybe they scratch a few clauses here and there, provide notes, etc.). It would be great if the app had an OCR and can detect the revisions provided by the insurer. If this is the case, we need to integrate email into this app's workflow so we can communicate back-and-forth with the insurer with Rekonvia staying in the loop.
   - Or, if they agree with our QS, they can simply approve it via email. We need a way to feed this agreement into the app so we can move forward.
- **Irfan's Notes:**
   - For this demo, let me know if we can integrate some kind of email system into this app. Recommend me something that can be incorporated easily into this app. Ask me questions if needed.

## 3. Client Proposal

- **Falih's Quotes:**
   - The current client side of the app is great. It's very simple, they can review our proposal (PDF), see the Excel file containing the list.
   - The clients should have a way to give us notes regarding the proposal so we can change them.
   - This rarely happen, but some clients can make us go back-and-forth with them regarding the contents of the proposal. Let's say one of their buildings' sum insured is changed, this will automatically adjust the premium. If the premium goes up, clients would likely ask for more discount.
   - We the brokers usually retain the current discount, per OJK rules. But it would be useful to have some sort of an optional step to finalize the premiums and discounts with the client, should they get nosy about this.

## 4. Data Reconciliation

- **Falih's Quotes:**
   - I'm not sure if this step is strictly necessary, because if the client already approve, the data should be good.
   - **Irfan's Interpretation:** I assume since AI already done most of the checks in step 1.
   - So maybe this "Data Reconciliation" step could be used just to see a recap of what was updated for/from the client.
   - I think we can merge this step with "5. Final Review + Binding". But to be safe, maybe at this point, we can re-confirm the new property value, its' sum insured, and the adjusted premium.
   - During final review, I think there shouldn't be more manual reviews by the human users. Clients mostly only care about premiums, they rarely pay attention to the clauses.
   - So, the step up from Proposal to Draft Final Slip (DFS) most likely will contain the same clauses, only differs in the premium.
   - When binding the final Word file, in the last page, there should be room for broker remarks and the signature from the insurer.

# Proposed Rekonvia UX overhaul plan

The key change is to make AI an active first-step assistant while keeping human authority explicit. The current manual lifecycle and server safeguards should remain intact.

## Target workflow

1. **Renewal materials**
   - Upload the previous Final Slip/Cover Note and latest Standard T&C.
   - AI compares both and produces clause differences.
   - Upload the Excel schedule or download/use the standard template.
   - Broker reviews findings and generates the QS.

2. **Insurer review**
   - Record insurer correspondence manually or through email integration.
   - OCR annotated PDF revisions.
   - Broker reviews each change and records the insurer response.

3. **Client proposal**
   - Publish the proposal.
   - Client adds notes and confirms location/sum-insured changes.
   - Renewed premium adjusts through the existing decimal calculation engine.
   - Optional discount conversation remains separate from the confirmed data.

4. **Final review and binding**
   - Show a concise recap of client-approved updates.
   - Generate DFS.
   - Broker adds remarks and external binding evidence/signature space.
   - Reconciliation is folded into this stage rather than a separate workflow phase.

The broker’s role remains review and facilitation; the client remains the source of current risk data.

## Phase U0: UX and tour foundation

**Goal:** Prepare the app for major navigation changes without risking domain behavior.

Changes:

- Restore and improve the first-use tour.
- Add **Repeat tour** under the authenticated account menu for broker and client accounts.
- Make tour progress role-aware.
- Add explicit stage “next action” summaries.
- Add a small onboarding checklist for:
  - upload sources;
  - generate QS;
  - record insurer response;
  - publish proposal;
  - complete client confirmation.

Existing implementation: `Tour.tsx` and `WorkspaceChrome.tsx`.

Acceptance:

- New and returning users can access the tour.
- Touring never changes case data.
- Hidden/closed tour state survives reload.
- Existing drafts and AI preparation remain unaffected.

## Phase U1: Simplify navigation and add brokerage settings

**Goal:** Remove low-value steps and establish controlled renewal references.

Changes:

- Reduce the broker sidebar to four stages:
  - Renewal materials
  - Insurer review
  - Client proposal
  - Final review and binding
- Remove “Wording” as a first-stage tab.
- Move Standard T&C into a versioned brokerage settings screen.
- Keep the standard wording available to AI and quote generation.
- Preserve individual baseline/approved wording history as evidence.
- Add Superadmin roles and a permissions matrix:
  - manage users;
  - assign brokers/clients;
  - manage Standard T&C;
  - optionally delegate T&C maintenance.
- Keep ordinary brokers free from formal approval authority.

Backend:

- Versioned Standard T&C documents.
- Brokerage role and permission records.
- Immutable T&C publication history.

Acceptance:

- Brokers can complete the workflow with fewer tabs.
- Only authorized users edit Standard T&C.
- New T&C versions do not silently rewrite old cases.
- Historical clauses remain linked to the version active at that time.

## Phase U2: Make AI-first clause review the entry task

**Goal:** Automate the highest-value comparison identified by Falih.

Changes:

- On opening “Renewal materials,” make the primary action:
  - **Compare prior Final Slip against Standard T&C**
- Let AI produce a review queue containing:
  - new or strengthened clauses;
  - removed clauses;
  - modified wording;
  - unchanged clauses;
  - unresolved matches.
- Present each finding with:
  - source document and excerpt;
  - prior wording;
  - standard wording;
  - recommended action;
  - accept/reject/follow-up status.

The existing manual source inventory remains the authority. AI findings never alter canonical wording automatically.

Backend:

- Reuse the existing broker-private AI batch infrastructure.
- Persist finding status and broker review separately from renewal state.
- Reuse source hashes and immutable document versions.

Acceptance:

- Every finding is traceable to both source documents.
- Accepting a finding changes only a draft recommendation until the broker confirms it.
- AI unavailable or rate-limited leaves the complete manual comparison available.
- No AI result establishes insurer or client approval.

Reference: `ai-assistance.md`.

---

## Phase U3: Excel schedule import and QS assembly

**Goal:** Replace the current manual schedule process for the MVP.

Changes:

- Provide a standard downloadable Excel template containing:
  - location name;
  - address;
  - occupancy;
  - sum insured;
  - rates;
  - deductibles;
  - remarks.
- Allow upload of a completed schedule.
- Prepare extracted rows and validation warnings in a review table.
- Highlight mismatches between Excel, prior schedules and client-confirmed location data.
- Optionally compare occupancy/rates against a versioned OJK reference document.
- Embed the final schedule into the QS Word output rather than attaching a separate operating file.

Pricing remains exact through the existing decimal engine.

Backend:

- Store schedule versions and row provenance.
- Import only finalized XLSX files.
- Keep calculated premiums separate from insurer-recorded premiums.

Acceptance:

- Users can review and correct every imported row before continuing.
- Missing addresses, occupancy, currency or sums are visibly blocked.
- The generated QS embeds the reviewed schedule.
- Gross premium is shown independently from the 15% illustrative/negotiated discount.
- OJK matching is clearly labeled as a reference result, not a legal determination.

## Phase U4: Insurer communication and annotated response

**Goal:** Keep external insurer coordination inside Rekonvia rather than losing its evidence in email threads.

Start with a provider technical spike:

- recommend a provider with verified inbound email webhooks;
- test PDF attachment extraction;
- test thread/case routing;
- verify retention and privacy handling;
- measure complexity against the existing Supabase backend.

Changes:

- Give each case a dedicated Rekonvia inbound/outbound communication thread.
- Record manual external email response when automatic integration is unavailable.
- Upload annotated insurer PDFs.
- OCR or extract PDF revisions and map them to quotation clauses.
- Detect:
  - deleted or inserted clauses;
  - crossed-out wording;
  - insurer notes;
  - approval versus amendment versus follow-up.
- Record the broker’s disposition for every finding.
- Detect simple insurer approval emails and present as broker-confirmed external evidence—not a simulated insurer account.

Acceptance:

- One email/PDF response is linked to the exact QS/option version.
- OCR results remain suggestions requiring broker review.
- Manual response recording continues to work when email delivery or OCR fails.
- Individual participating insurers remain separate; leader approval never implies the whole panel.

This phase is worth a provider decision and prototype test before backend expansion.

---

## Phase U5: Simplify client interaction and renewal negotiation

**Goal:** Let clients change data and discuss proposals without exposing broker-side information.

Changes:

- Keep the client workspace focused on:
  - proposal;
  - locations;
  - renewal instruction;
  - response history.
- Add structured client note fields to the proposal.
- Let clients propose:
  - changed sums insured;
  - changed locations;
  - corrected occupancy/address;
  - premium or discount questions.
- Recalculate premiums immediately as proposals change.
- Preserve historical values and show old/new values side by side.
- Make discount negotiation optional rather than a separate mandatory stage.
- Automatically invalidate prior agreement when materially revised proposal data changes.
- Keep client confirmation as the source of truth for locations and sums insured.

Changes should return to the broker as a review queue rather than directly updating approved case facts.

Acceptance:

- Client comments cannot silently alter canonical risk data.
- An accepted sum-insured change updates the premium before re-publication.
- A new proposal requires new client agreement.
- Broker remains unable to enter client-confirmed sums or locations on behalf of the client.
- Discount questions do not block binding unless the brokerage chooses to make them mandatory.

---

## Phase U6: Merge reconciliation with final review and binding

**Goal:** Finish with a concise, evidence-based control check.

Changes:

- Fold reconciliation into **Final review and binding**.
- Replace broad manual review sections with a generated recap:
  - client-confirmed location changes;
  - adjusted sums insured;
  - premium and discount changes;
  - latest accepted clauses;
  - unresolved insurer conditions;
  - outstanding evidence.
- Remove redundant manual approvals.
- Generate DFS when every required fact is current.
- Add broker remarks to the final Word file.
- Add reserved room for insurer signature/acknowledgment evidence.
- Preserve individual insurer acknowledgment rather than treating leader signature as panel-wide.

Acceptance:

- Final review has no hidden prerequisite.
- All blocked items link to the responsible stage and actor.
- DFS contains only the latest client-confirmed and insurer-supported terms.
- Binding evidence identifies each insurer and document version.
- Exported Word files remain editable.

## Phase U7: Pilot hardening and researcher retest

**Goal:** Turn the overhaul into a stable MVP.

Priority checks:

- one brokerage, multiple brokers and clients;
- role and permission boundaries;
- first-time and repeat tours;
- local and hosted data consistency;
- conflict/replay behavior;
- upload and AI failures;
- Excel/OJK reference changes;
- email/OCR provider outages;
- client proposal revisions;
- final Word exports;
- mobile and tablet workflows;
- English and Indonesian terminology.

Use 5–10 real renewal-style tasks with Falih and 2–3 brokers.

Measure:

- time to first QS;
- clause differences correctly identified;
- clause differences missed;
- spreadsheet rows corrected manually;
- insurer PDF revisions detected;
- client revision rounds;
- intervention count;
- AI/provider failures;
- time to final Word export.

This phase should report AI usability separately from AI factual accuracy.

## Deferred from the MVP

- Insurance policy administration
- Endorsements
- Invoicing
- Automated insurer identity verification
- General-purpose AI chat
- Automatic binding approval
- Multilateral insurer workflows not represented by the case
- Claims administration
- Singapore/Australia rule engine

Skipped: we did not invent or implement the email/OJK provider choices, and no UI code was changed. Risk: the overhaul is most valuable when each AI feature remains advisory; an overly aggressive “AI completed” status could create false regulatory or approval confidence.
